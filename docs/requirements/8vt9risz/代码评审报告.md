### 3.2 建议（4 条）

#### S-1（建议）同一次保存/返回路径上 `reloadConfig` 执行两次

- **位置**：`flutter_app/lib/screens/settings/api_config_screen.dart:216-220`、`flutter_app/lib/screens/chat/chat_screen.dart:89-100`。
- **证据**：`_save` 已 `saveActive`，并在 `pop` 前调用 `reloadConfig()`（未 await）；`_openApiConfig` 在路由 pop 后又 `await reloadConfig()`，且不区分保存/取消——`Navigator.push` 的 `bool?` 结果被丢弃。
- **风险**：保存路径重复读一次存储；未保存返回也做一次无意义 reload；若后续 `reloadConfig` 增加状态通知、埋点等副作用，会执行两次；两处 reload 的所有权不清晰。
- **方向**：收敛到一处。推荐 `_save` 内 `await reloadConfig()` 后再 `pop(true)`，`_openApiConfig` 只负责 `push` 与结果处理；或让 `_openApiConfig` 读取 `saved` 结果，保存路径依赖 `_save` 的 reload，取消路径不 reload。

#### S-2（建议）预设的「渲染基线」和「保存基线」是两套独立推导

- **位置**：`flutter_app/lib/screens/settings/api_config_screen.dart:56-60`（initState 的 seed）与 `:201`（`_save` 的 baseline）。
- **证据**：initState 用 `AiConfig.defaultFor(initialProvider)` 铺表单；`_save` 又用 `AiConfig.defaultFor(_provider)` 生成保存基线。两条路径各自生成 `id`，并依赖「`_provider` 只在 `_applyPreset` 中变化」这一隐式约束。
- **风险**：当前两条路径结果一致（`_provider` 初值来自 `initialProvider`，`_applyPreset` 会同步所有字段），但未来若新增只改 `_provider`/`_apiFormat` 的入口，页面显示与落库内容会分叉；seed 的 `id` 被丢弃，排查「为什么保存出另一个 id」时多一层困惑。
- **方向**：在 initState 保存 `late final AiConfig _seed`，`_save` 使用 `widget.config ?? _seed`；或抽出 `_baselineFor(provider)` 让两条路径共用，并补一条「预设页保存后 baseline 不变」的断言。

#### S-3（建议）缺少「预设页 → 填 Key → 保存 → 激活配置完整」的自动化用例

- **位置**：`flutter_app/test/api_config_screen_test.dart`（仅渲染断言）、`flutter_app/test/welcome_app_test.dart`（只到进入配置页/返回，不点保存）。
- **证据**：现有用例覆盖预设字段渲染和路由跳转，但没有点击 `api_config_save` 后断言 `AiConfigStore().loadActive()`；`_save` 的 baseline、`hasCompleteFields` 与「保存后配置生效」的联动只能手工验证。
- **风险**：若 `_save` 的 baseline 或 Key 写入回归，现有测试仍全绿，但本需求最关键的一步失效；后续复审也没有自动化信号。
- **方向**：在 `api_config_screen_test` 加一个保存用例：`SharedPreferences.setMockInitialValues({})` → pump `ApiConfigScreen(initialProvider: deepseek)` → 填占位 Key → 点 `api_config_save` → 断言 active 配置的 `baseUrl`/`mainModel`/`apiKey` 与 `hasCompleteFields == true`；或在 app 测试里从欢迎弹窗走到保存，断言回到首页后配置非空。

#### S-4（建议）`runOnce` 的 Future 现在跨越整个配置页生命周期

- **位置**：`flutter_app/lib/settings/welcome_controller.dart:119-122`、`flutter_app/lib/screens/chat/chat_screen.dart:89-100`。
- **证据**：`onConfigureAi` 内 `await Navigator.push(...)`，push 的 Future 在配置页 pop 时才完成；控制器 `await onConfigureAi()`，因此 `_run`/`runOnce` 的 Future 会 pending 到用户离开配置页。技术方案 §3.3 明确选择了「等待导航」，但 `Navigator.push` 的返回 Future 不会把路由 builder 的渲染错误抛给调用方，能捕获的主要是同步 push 异常。
- **风险**：`runOnce` 的「本次门控完成」语义被拉长到一次用户会话；期间再次调用 `runOnce` 会静默复用未完成的 Future；未来若有启动流程 `await runOnce`（如启动页门控），会被配置页阻塞。
- **方向**：保持 `dismissed` 先于导航；让 `_openApiConfig` 自己负责导航后的 reload 与错误处理，控制器只负责发起 push（不 await 路由生命周期）。若保留 §3.3 语义，请在 `runOnce` 文档里明确 Future 会跨越配置页，并补一条「配置页打开期间并发 `runOnce` 返回同一 Future」的测试。
